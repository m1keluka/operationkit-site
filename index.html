The field left something open

Every other platform ships empty.

Look at the agent tools available today: Hermes, OpenClaw, OpenHands, Flowise, CrewAI. Most install in one command. That part is solved. What you get after the install: a blank, single-user assistant, no roles, no isolated workspaces, and a configuration gap you fill yourself. The moment a second person joins, or you need to serve multiple clients from one deployment, or you need a review gate on agent output, every one of them either cannot do it or sells you a paid enterprise tier to unlock what should have been there from the start.

OperationKit is what you get when you build that layer ground-up instead of bolting it on.

Ships with agents and roles.

Not a blank canvas. A configured operation. Six-phase pipeline, C-suite agent personas, per-workspace context. Change any of it; it is all plain markdown you own.

Multi-tenant out of the box.

One deployment, many isolated workspaces, real RBAC. No per-seat SaaS fee. No sales call to unlock governance.

Governed by design.

Every objective goes through a fresh-context adversarial reviewer before it reaches you. The acceptance criteria are locked before the work starts. The reviewer auto-iterates on failures. You see results, not drafts.

Under the hood

Four layers. One-way dependency.

Tools → Skills → Agents. Edges are declared in frontmatter and validated by the okit CLI at authoring time. A dangling reference is a hard failure, not a silent warning. That is what "machine-checkable" means here: the graph is a fact, not a convention.

Objectives, not tasks.

Work lives on a Kanban board where every objective runs in its own dedicated session. A strategy objective decomposes itself into worker objectives and spawns them. Workers run, get reviewed, and report back. The delegator re-wakes on completion and decides the next step. Up to 25 concurrent sessions. SQLite-backed state that survives restarts.

A second agent grades every output.

When a working session finishes, a fresh-context reviewer reads the output against acceptance criteria that were locked before work began. It cannot see the worker's scratch notes, only the deliverable and the criteria. If it fails, the session reverts to working with the findings prepended. It iterates up to three times before escalating to you. This is not a linter. It is a separate agent with a separate context and a single job: refuse to pass what does not meet the bar.

# review gate - fresh context, criteria locked up front working → ai_review auto ai_review → working verdict: FAIL (findings prepended) ai_review → human_review verdict: PASS (project-type only) ai_review → done verdict: PASS (task/bug type)

Context that loads in the right order.

Each session assembles four tiers before the model sees a single token. Global routing rules load first. The agent persona loads second. The workspace business context loads third. The user profile loads last. Late-loaded knowledge cannot override a stable rule. Most agent harnesses have one tier: a system prompt. Some have two. OperationKit has four, validated at authoring time by okit validate.

Tools, skills, agents. Every edge is declared.

53 tools. 82 skills. 19 agents. Each skill declares which tools it calls. Each agent declares which skills it loads. okit validate walks the graph and hard-fails on any declared slug that does not resolve. A skill that references a tool that has been renamed is a build error, not a runtime surprise. The graph is machine-checkable. That is the thing no other system in the field currently does.

Honest answers

Three things you are probably thinking.

I can already use Hermes or OpenClaw. They install in one command.

They do, and that part is solved. After the install, you have a blank single-user assistant with no roles, no isolated workspaces, and no review gate. You assemble the rest yourself. OperationKit installs from your API keys too. The difference is what's there when it's done.

What about my API keys? Is this safe?

OperationKit is not a security sandbox. It runs on your server, in code you can read. Your keys do not leave your machine. There is no vendor layer between your credentials and the model provider. If your threat model requires a hardened managed SaaS, this is not it. If "I need to see every line of code that touches my keys" is the requirement, this is built for that.
